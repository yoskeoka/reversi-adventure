# table32 の学習局面を段階的に増やす

> **Execution**: Use `/execute-task` to implement this plan. After implementation is complete, use `/review-task` to prepare and create the PR.

Addresses: N/A. 0018 の受け入れや現行モデルの採用は別の作業。

## 目的と完了条件

0056 の試作ではデータ生成、教師作成、学習、対局まで通った。phase 10 の train は12局面で、
学習で観測した重みアドレスは621件だった。規模拡大では、同じ行の更新回数を増やすより先に、
実際に異なる局面と盤面パターンを学習用に増やす。

人間が局数・時間・RSS の予算と段階を指定し、追加データ生成、教師作成、学習、候補結合、
独立対局までを再開可能な単一の入口で進められること。保存済みの棋譜と教師を次段階へ引き継ぎ、
データが足りない phase・split に生成予算を振り、各段階の増分と停止理由を offline で再現する。
実装の完了は fixture で一連の経路を検証し、運用コマンドを提示した時点とする。計測と本番処理は
人間が開始する。0058 の実装 [PR #309](https://github.com/yoskeoka/reversi-adventure/pull/309)
が main に入ってから本計画を実装する。固定序盤を学習する本番段階は、その段階で必要な
0058 のラベル shard が検証済みであることを要する。

## 現行の入口と不足

- `tools/reversi-ai-training/table32_data.py:17–58` の 0058 入力設定は、0–9 の固定 corpus と
  ラベルおよび 10–59 の split 別最低数を選べる。1 root に生成 prefix は１つで、旧方式の
  `--import-games-from` と併用できない。
- `table32_inputs.py:35–99,165–184,232–283` は種から合法な開始手順を選び、既存の自前
  プレイヤーと終局結果から後続 phase の教師を得る。現行のゲーム ID は seed の違いを
  表さないため、別 root の既存 ID だけでは追加ゲームを識別できない。
- `table32.py:627–675` は予定ゲームを生成・保存してから抽出を１回行う。最低数に届かなければ
  学習前に停止し、同じ root にゲームを足す経路はない。`table32_extract.py:67–166` は
  D4 正規化、split 間重複の除外と、phase 別の採用局面・局数を集計する。
  `table32_import.py:34–108` の既存実装は旧 run の単一 root と厳格な split 判定を前提にする。
- `table32_combine.py:120–181,231,293–343` は S0、StrategicEvaluator、一様ランダムとの独立比較を
  固定した対局数で行う。明示した相手との比較モードには、既存の20→200局の継続がない。
  開始局面が10手以降のため、序盤の評価関数はこの比較で使われない。
- `table32_optimizer.py:166–177` の validation MSE は現行 optimizer 内部の学習率制御に使う。
  `table32_store.py:149–155` は既存の S0 対局で20局10点以上、200局100点超を判定する。

## 黒箱仕様に追加する契約

1. **局面を増やす単位**は、固定された prefix 群・split・seed 範囲を持つ追加棋譜 shard とする。
   phase の不足に応じて、そこへ到達しうる複数の開始 prefix と独立 seed を指定できるようにする。
   10–59 の教師は現行の自前方式を維持し、空き20以下の完全読みも維持する。
   0–9 は 0058 の検証済み固定ラベルを使う。部分集合を拡大する場合は、段階ごとの選択を
   決定的かつ累積可能にし、phase の先頭に偏らないようにする。学習に使える局面が少ない
   phase では列挙結果と予約除外後の最大数を明示する。
2. **独立性と再利用**を段階をまたいで維持する。同じゲームを別 split に動かさず、ゲーム ID を
   shard identity と組み合わせる。盤面と手番を D4 正規化した重複を扱い、0018 の予約および
   既知の露出を適切な split と独立対局から除外する。重複除去で脱落した行を実績に数えない。
   検証済み shard は digest を固定して参照し、新規 shard と組み合わせる。既存 root を上書きせず、
   設定変更は新しい段階 manifest に記録する。
3. **データ量による判断**を明示する。各 phase・split の累積と純増の unique 局面数、採用局数、
   到達数、重複・予約除外数と prefix 別の内訳を記録する。学習用パターンは phase 別に
   観測アドレス数と出現頻度を報告する。設定された局面・局数の下限に満たない場合は学習を
   開始せず、不足した範囲に次の shard を割り当てる。生成予算を使い切った場合や、設定した
   連続 shard 数で unique 局面が増えない場合は、対象と停止理由を保存する。validation・test の
   不足は別枠で補い、固定序盤を train に全件使った phase は独立 split の欠測を記録する。
4. **対局による判断**をデータ量の判断から独立させる。MAE・MSE は診断と現行 optimizer 内部の
   制御に残す。学習済み候補は新しい開局で先後を交換し、まず S0 と20局対戦する。10点未満なら
   予算内で次段階のデータを足して新候補を学習する。10点以上なら同一候補を200局まで延長し、
   最初の20局の証跡を再利用する。100点以下なら予算内で次段階へ進み、100点超なら有望として停止する。
   予算上限に達したら最良の観測結果と停止理由を残す。StrategicEvaluator・ランダムとの対局は
   個別の診断に使う。評価に使った開局は次段階の最終 holdout に再利用しない。
   序盤ラベルの寄与を調べるときは、予約や露出を除いた開局で、探索が phase 0–9 の学習表を
   実際に参照する別条件を設け、参照の証拠を fixture で確認する。
5. **実行と再開**では、段階・生成/教師/抽出/学習/対局/検証の境界と、各段階の既知総数を
   記録する。完了単位は順にゲーム、教師付きゲーム、phase/split、学習 checkpoint、対局、
   検証対象の receipt。生成・教師が同一ゲームで一体化している既存経路は同じ完了単位にできる。
   spec に進捗形式 `table32-scale round=N stage=STAGE unit=ID completed=N total=N elapsed_seconds=S status=STATUS`
   と既定の表示間隔10単位、`--progress-every`、開始・終了・停止時の表示を固定する。
   中断後は完了単位と入力の digest を照合し、未完了分だけ処理する。検証は外部プロセスを起動しない。

## 検証

- 小規模 fixture で、異なる prefix・seed の shard を増やすと unique train 局面が増えること、
  既存 shard の再生成がないこと、予約・D4 重複・split 漏洩が件数に混ざらないことを確認する。
- 学習前の不足、純増なし、時間・局数予算停止、途中再開、履歴や設定の改変拒否を確認する。
  同一入力で再開した候補と検証結果が中断なしの結果と一致することを確かめる。
- 固定ラベル不足が明示され、phase 0 のラベル、10–59 の自前教師、既存 0056/0058 の検証が
  保たれることを確認する。追加の fixture で20局の通過・不通過、200局への延長、候補の
  同一性・開局の独立性、200局の判定と MAE・MSE に依存しないことを確認する。
- 関連 `test_table32*.py` と CLI fixture、変更した層の lint、workflow lint、
  `git diff --check` を通す。
